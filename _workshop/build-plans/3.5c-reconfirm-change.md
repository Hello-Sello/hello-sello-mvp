# 3.5c - Re-confirm a changed version

**Status:** ✅ DONE (essentially free, verified 2026-06-11). **Owner:** Ayush. **Builds on:** 3.5b (edit), 3d (gate).

> 3.5c = after an edit, both sides must re-confirm the NEW version. This needed almost no new code, because of
> the immutable-versioning design: `deal_confirmation` is keyed per `(card, version)`, so when 3.5b bumps the
> version, the new version simply has no confirmations - both seats read `pending` automatically, and 3d's
> existing `ConfirmBar` + `confirmDeal` re-run on the new version unchanged. Verified live: after editing the
> test deal v1→v2, both seats reset to "not yet" and the card dropped back to `draft`.

## What was (not) built

- **No new code.** The version bump in `edit_deal_draft` (3.5b) is the whole mechanism; 3d's gate is reused.
- **Verified:** DB showed `confirmations on v2 = 0`; the card UI showed both seats "not yet" + Confirm/Decline.

## Possible future polish (not required)

- A small "this version changed - please re-confirm" cue on the card (the gate already says "Both sides must
  confirm", which is accurate). Could surface the latest change note next to the gate. Low priority.
- `amended` status semantics (today an edit drops the card to `draft` so 3d flips it; a dedicated `amended`
  status would need `confirmDeal` to handle it). Deferred.

## Lesson

Good data design pays itself back: keying the gate to a version meant a change auto-invalidates the old
agreement with zero extra logic. See the 3.5a/3.5b insight - "the rule enforces itself."
