## 0. The problem (the three knots)

Today acceptance is tangled because the card is asked to do two jobs - **show** the deal and **ask** for a
decision - and because manual-create births the card too early.

1. **Accept-your-own-deal.** Manual create calls `create_deal_draft` immediately, so the card is born and its
   `ConfirmBar` (the Seal gate) shows the creator a "Confirm deal" on a draft they just made.
2. **Orphan workspace.** `create_deal_draft` builds card + workspace + thread in one transaction *at create*,
   so a never-accepted manual deal leaves an empty workspace.
3. **Sella has nowhere to ask.** Sella may not create a card (the AI fence), yet acceptance lived on the card -
   so a *detected* deal had no allowed place to ask for acceptance.

All three share one root: **the card is born before anyone accepts**, and **acceptance has no home that is not
the card**. 4.5 fixes both.

## 1. The model (one birth path, two doors)

```
            MANUAL door                         SELLA door
   person fills "Start a deal" form     Sella detects product+qty / product+price
                 |                                    |
                 v                                    v
        ┌──────────────────────────────────────────────────────┐
        │   PROPOSAL  =  a chat message (NOT a card, NOT a new   │
        │   deal status). Holds the draft + per-company votes.   │
        │   Manual: proposer's side vote = ACCEPT (sending = yes)│
        │   Sella : both votes = null                            │
        └──────────────────────────────────────────────────────┘
                                 |
                 both votes = ACCEPT  (human click only)
                                 |
                                 v
        ┌──────────────────────────────────────────────────────┐
        │   BIRTH = atomic create_deal_draft                     │
        │   card + lines + private + workspace + 2 owners +      │
        │   thread + log + audit  (one transaction)             │
        └──────────────────────────────────────────────────────┘
                                 |
                          negotiate (editDeal)
                                 |
                 both SEAL (deal_confirmation, 3d gate)
                                 |
                                 v
                          Confirmed (golden card)
```

**The proposal is the pre-card object.** Detection already proves this works - the `deal_detected` message
*is* the proposal, its `metadata.votes` *are* the acceptance, and birth happens on both-accept. We make manual
create produce the **same** kind of message. So: **one birth path, two entry doors.** No new card status, no
notifications backend, no splitting the birth transaction.

## 2. Decisions locked with Ayush (2026-06-14)

- **D1 - One birth path for both doors.** Manual create and Sella detection both write a **proposal message**.
  Reuse the existing `deal_detected` message + metadata shape, discriminated by **`metadata.source = 'manual' |
  'sella'`**. The card is NOT born at propose time. (Keeping the historical `deal_detected` `type` avoids
  migration churn on shipped, working detection; the `source` field carries the difference. UI copy: "Sella
  spotted a deal" vs "{name} proposed a deal".)
- **D2 - Sending = accepting (manual).** The proposer's company vote is pre-filled **`accept`**; only the other
  side is pending. (Kills "accept-your-own-deal".) Sella detection: both votes start `null`, both must accept.
- **D3 - Birth only on both-accept, atomic.** `confirm_detected_deal` → `create_deal_draft` runs **only** when
  both votes are `accept`. No orphan workspace, no premature card. **Supersedes 3.5a D5.**
- **D4 - The proposer is the initiating company.** Birth must read `initiating_company_id` from the proposal
  (`metadata.proposed_by_company`), NOT from whoever clicks accept last. This also seeds offer/order direction
  (seller-proposed → offer, buyer-proposed → order). Precise labelling rule stays parked (→ Marcel), but the
  hook lands here. **Required tweak to `confirm_detected_deal`.**
- **D5 - The card is PURE DISPLAY.** Remove `ConfirmBar` from `CardFront`. The card only shows terms, parties,
  values, products, logs (+ the golden Confirmed state). Every *action* leaves the card.
- **D6 - The Sella strip is the single action surface.** The deal / "Talking about" bar (`DealPin`) is rebuilt
  into the **Sella strip**. It owns: birth-accept (the proposal), the change-note ask, and the Seal gate. It
  shows the AI "thinking" animation + the EU-AI-Act "AI" badge.
- **D7 - Shared vs private split (neutrality).** The strip is the **shared, neutral** surface - both sides see
  the same thing and press the same buttons. It is system-voice only: structured asks (Accept, "why this
  change?"), never a free chat. **Private "ask Sella" Q&A stays in the right panel** (`SellaPanel`). The strip
  must never hold a one-sided conversation.
- **D8 - The change-note moves to the strip.** After an edit (`editDeal`), Sella asks "why this change?" in the
  strip; the answer feeds the existing `deal_change_input` / `deal_card_log`. The buried note field at the
  bottom of the edit screen is removed (it is the reason people skip the note today).
- **D9 - One strip = one selected deal.** The strip is bound to a single selected deal (default = the latest),
  so Sella is grounded to "which deal are we talking about." The strip dropdown switches the selected deal and
  the card follows. Asks for *other* deals do not crowd the strip - they collect in a **notification icon in
  the chat header**; clicking one switches the selected deal.
- **D10 - Decline / withdraw.** **Decline** → `confirm_detected_deal(reject)`; Sella posts a system message
  ("Proposal declined") both sides see; the strip resets to "+ Start a deal". **Withdraw** (proposer pulls back
  before the other side engages) → mark the proposal withdrawn (`metadata.withdrawn=true`) and reset quietly,
  no system message (the other side had nothing to react to). No card is born either way.
- **D11 - Header chrome by deal presence.** No deal yet → minimal header + "+ Start a deal" (the screenshot).
  Once a deal exists → the relationship + workspace + notification icons appear; the workspace icon only after
  birth. "+" (bottom-right) starts another deal.
- **D12 - The AI fence holds.** Sella only ever *suggests* (the proposal message). The human's Accept click
  (server action → RPC) is the only write that births a card. Sella never creates a card.
- **D13 - Scope = connected-P2P only.** Parked: not-connected → inbox / connection-gate; C2C trading-ticketing;
  shop / offer Path A; the global app-wide notification system.

### Decisions added 2026-06-15 (the deal-CHANGE rethink; full context in `6-pending-map.md`)

- **D14 - Vocabulary: Note vs Change reason.** **Note** = an optional, per-company content note shown on the
  card face (a highlight for the other side). **Change reason** = the required reason on every Accept/Decline of
  a change, into the log. Never call the Change reason a "note." (6-pending-map §1.)
- **D15 - An edit is HELD until both accept.** A pending change does not touch the live card; a decline discards
  it. **Supersedes "an edit commits immediately."** The backbone - reuse the birth/propose pattern for edits.
  (6-pending-map T1.)
- **D16 - The gate is Accept / Decline ONLY.** No Counter; **Withdraw is removed** (from `confirmDeal` /
  `ConfirmBar` / the strip). **Supersedes the Withdraw half of D10.**
- **D17 - A human edit auto-accepts the editor's side**, leaving the other side pending.
- **D18 - Announcements split by outcome.** Accept → a system message in the **deal chat**; Decline → a system
  message in the **p2p chat** (never the deal chat, because the card did not change). Supersedes today's
  fire-on-edit / over-broadcast behaviour.
- **D19 - Sella-detects-changes moved to 5A.5.** Detecting a change to an *existing* card (not a new birth) is
  new Sella work that rides the next Sella build. (6-pending-map T6.)
- **D20 - C2C ticketing + the connected/not-connected differentiator parked** to a future chapter (reuse the
  inbox assignment primitive). (6-pending-map T7/T8.)

## 3. The Sella strip (the surface)

The strip is the rebuilt deal bar in `DealPin`. It has three states. The bar runs full width: **left = "Open
card"**, **center = Sella line / asks (thinking animation + AI badge)**, **right = deal number**; a small
**dropdown** switches the selected deal.

- **State A - no deal, no proposal.** Just a dashed **"+ Start a deal"** (the screenshot). Header is minimal.
- **State B - a proposal is pending.**
  - *You must act* (you are the other side): the strip shows the proposal summary + **Accept / Decline**
    (this is birth-accept → `confirm_detected_deal`).
  - *You proposed it* (manual, your side pre-accepted): "Proposal sent - waiting for {other}" + **Withdraw**.
  - *Sella detected* (both pending): both sides see Accept / Decline.
- **State C - a deal is selected (live card).** Deal chip + status; "Open card" (left), deal number (right),
  the deal dropdown. Sella's asks drop down from here:
  - **Change-note** - "why this change?" (after `editDeal`) → `deal_change_input`.
  - **Seal** - "Confirm final terms" - the two-seat face (reused from `ConfirmBar`) → `confirmDeal`.
  - **Notices** - the "why it changed" summary (4d), card-linked.
  - The **thinking animation** plays while Sella is computing (detect / summarize running).

Neutral, both-sides, system voice (D7). The right panel (`SellaPanel`) stays the *private* per-side Sella.

## 4. What changes (code + DB)

### DB / RPC (small footprint - no new table, no new deal status)

- **NEW `propose_deal(...)` [SECURITY DEFINER].** Writes a `deal_detected`-shaped **proposal** message into the
  p2p thread: `metadata.source='manual'`, `proposed_by_company = session company`, `votes = { proposer: accept,
  other: null }`, `draft` from the form. Does **not** birth. (An RPC is needed because RLS today only lets Sella
  / service-role insert `deal_detected`; this mirrors `confirm_detected_deal`.)
- **TWEAK `confirm_detected_deal`.** Read `initiating_company_id` from `metadata.proposed_by_company` (fallback
  to the confirmer for legacy symmetric detection). Verify it births correctly when one vote was pre-filled
  (manual). (D4)
- **NEW `withdraw_proposal(message_id)` [SECURITY DEFINER].** Proposer-only, only while the other vote is null;
  stamps `metadata.withdrawn=true`. (D10)
- **Seal - no DB change.** `confirmDeal` + `deal_confirmation` + the 3d gate logic are unchanged; only the UI
  host moves (card → strip).
- **Change-note - no DB change.** Reuse `editDeal` → `deal_change_input` / `deal_card_log`; the strip supplies
  the note. (D8)
- **Cross-deal header notification - a READ only.** `listRelationshipDealAsks(relationshipId, viewerCompany)`
  derives pending items (proposals with viewer vote = null + deals awaiting the viewer's seal seat). No table,
  scoped to this relationship. (D9)

### Components

- **`DealPin.tsx`** (the big one) - rebuild the bar into the **strip** (States A/B/C); render proposal
  accept/decline (B); host the change-note ask + the Seal two-seat face (C dropdown); the deal dropdown; the
  thinking animation + AI badge. Wires: `confirm_detected_deal` (accept/decline), `withdraw_proposal`,
  `confirmDeal` (seal), and the change-note → `editDeal`.
- **`CardFront.tsx`** - **remove `ConfirmBar`** (D5). Keep the golden Confirmed state. Card = pure display.
- **`ConfirmBar.tsx`** - re-home the two-seat face *inside* the strip's Seal dropdown (keep it "dumb + fed";
  same `{ seats, viewerSide, onConfirm, onDecline, onWithdraw }` contract).
- **`CreateDealForm`** (mounted in `DealPin`) - submit now calls **`proposeDeal`** (not `createDeal` /
  `create_deal_draft`). It becomes "Send proposal." Still "dumb + fed" (Sella can fill `initial` later).
- **`actions.ts`** - add `proposeDeal`, `withdrawProposal` server actions (wrap the RPCs). Keep `confirmDeal`
  (seal) and `editDeal` (change). The direct-birth manual path (`createDeal` → `create_deal_draft`) is retired
  for the manual door - birth now only via accept.
- **`MessageBubble.tsx`** - render the proposal message as a **quiet, card-linked notice** (the strip is the
  actionable surface; the message is the chat record). Handle both `source` variants.
- **`ThreadView.tsx`** - header chrome by deal presence (D11): relationship + workspace + notification icons
  once a deal exists; pre-deal minimal + "Start a deal". Notification icon → cross-deal asks → switch the
  selected deal.
- **`SellaPanel.tsx`** - unchanged in role: the **private** right-panel Sella (D7). (Polish is 5A.5.)
- **`sella-detect/index.ts`** - set `metadata.source='sella'` on the detected proposal so the unified path
  reads consistently. (Detection birth already routes through `confirm_detected_deal`.)
