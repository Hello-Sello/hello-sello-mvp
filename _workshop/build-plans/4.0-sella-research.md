# 4.0 - Sella research (shared, both agents)

**Status:** 🔬 OPEN - the first step of Section 4. **Owner:** COMMON - Ayush AND Muskan each do their own
research. Not assigned to one person.

> Section 4 = Sella. Before any Sella build (4a-4d, per Muskan's `DECISIONS.md` DEV-11) we both research
> Sella separately, then compare and lock. This is on purpose: Sella decides a lot of the chat + card UI,
> so the UI pass (Section 5) waits on what we learn here.

## Why a shared research step first

Sella is the part with the most open questions, and it touches both sides of the codebase (Ayush owns the
Connect/deal chat where Sella lives; Muskan has done the Sella *design* work - DEV-11, detection,
`propose_deal_draft`, stateless Bedrock). Doing the research in parallel and then comparing gives us two
independent reads before we commit to a build shape. It also lets the UI work (Section 5) start from a
settled Sella picture instead of a guess.

## What is already locked (from Muskan's design - do not re-litigate, build on it)

- **MVP Sella = stateless single-shot Bedrock calls** behind a 4a wrapper, each with ≤1 structured-output
  tool. **No agent loop / orchestrator / graph / framework / RAG / memory** for the MVP.
- The "5 Sellas" = **one runtime parameterised** by (scope · persona · tools), not 5 services.
- **Detection runs in a Supabase Edge Function** (new `chat_message` → DB webhook → Claude Haiku), NOT the
  Next.js path - keeps Sella a non-blocking leaf.
- **One `propose_deal_draft` tool**; suggest-only is structural (no confirm/send tool exists).
- Proposal + both-accept votes ride in the `deal_detected` message `metadata` - no new table.
- Workspace birth = one atomic transaction on both-accept.
- **The AI fence (load-bearing): Sella can FILL the deal form but NEVER commits.** Only a human button →
  server action writes. The `DealForm` is already "dumb + fed" for exactly this.
