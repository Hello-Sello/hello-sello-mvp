# 3.5b - Edit a deal (version bump + mandatory note + human Update)

**Status:** ✅ BUILT + verified live (2026-06-11, as Aurora/Alice; `tsc`+eslint clean; held in
`claude/ayush/work`, NOT dev). **Owner:** Ayush. **Builds on:** 3.5a (create), 3d (confirm gate).

> **Outcome:** edit works end-to-end via the atomic **`edit_deal_draft`** RPC. DB-verified on the test deal:
> version 1 → 2, value recomputed, **v1 lines kept frozen**, v2 snapshot written, private box carried forward,
> log + mandatory note recorded, **confirmations on v2 = 0 (gate auto-reset)**, `deal.amended` audit written.
> The mandatory-note gate verified live (Update disabled until a note is typed). Create + edit now share one
> `DealForm` (create + edit wrappers). **3.5c re-confirm falls out for free** - the version bump resets 3d's
> gate with zero extra code (confirmations are per-version).

> 3.5b is the EDIT side. A human edits a deal (lines, prices, terms, their own private box), writes a
> REQUIRED note, and presses Update. That commits a NEW version: the old version stays frozen (immutable
> history), the new one carries the changes, and both sides must re-confirm it. Reuses 3.5a's form shape and
> 3d's confirm gate. The commit is one atomic SECURITY DEFINER RPC (same pattern as 3.5a's create).

---

## 1. Decisions locked (from the 2026-06-11 chat + 3.5a build)

- **D1 - Anyone with access can edit** (both sides negotiate). Editor's company derived from the SESSION.
- **D2 - The note is MANDATORY** (Ayush, firm). Every change carries a human "why." Update is disabled until a
  note is typed. (Sella will later pre-write it; a human still presses Update - the AI fence.)
- **D3 - Edit = a NEW immutable version.** Bump `deal_card.version` N->N+1; snapshot the new line items at N+1;
  the old version's lines/confirmations stay untouched (the regulated-world "what was agreed, and when" proof).
- **D4 - A change resets the gate.** `deal_confirmation` is per-(card,version), so N+1 has no confirmations ->
  both seats read `pending` automatically. The card goes back to **`draft`** (re-negotiation) even if it was
  confirmed, so the existing 3d gate re-runs as-is (no confirmDeal change needed). The note explains the change.
- **D5 - Reuse the create form, prefilled.** The edit form is the create form's shape, pre-filled from the
  current card, plus a required note. ("Dumb + fed" - Sella can pre-fill the same edit form later.)
- **D6 - Carry forward the OTHER side's private box.** On a version bump the definer RPC copies all
  `deal_party_field` rows N->N+1 (so the buyer's patient price is not lost), then writes the editor's own value
  at N+1. RLS could not do this cross-company copy; the definer RPC can.
- **D7 - Atomic, same as 3.5a.** One `edit_deal_draft` SECURITY DEFINER RPC does the whole bump in one
  transaction (no half-edited card). Audit (`deal.amended`) stays in the app layer.

## 2. Schema - one migration (Phase 0)

- Add `audit_action_type` code **`deal.amended`** (lifecycle).
- Add the **`edit_deal_draft(...)`** RPC: auth + relationship-membership gate; require a non-empty note;
  bump version; `update deal_card` (version, status='draft', value_net, currency, terms, metadata, updated_by);
  insert new `deal_line_item` rows at N+1; copy `deal_party_field` N->N+1 then upsert the editor's value;
  append `deal_card_log` (origin deal_chat, person, "Deal updated to v{N+1}.") + the mandatory
  `deal_change_input` note. Returns the new version. No `deal_confirmation` writes (the bump resets the gate).
- `deal_card.version` + `deal_line_item.version` + `deal_party_field.version` already exist - no column change.

## 3. Phases

- **Phase 0 - migration:** `deal.amended` code + `edit_deal_draft` RPC. *Verify:* an edit via SQL bumps version,
  snapshots lines, carries party fields, writes log + note; old version intact.
- **Phase 1 - action + reads:** `editDeal(input)` server action -> RPC + `writeAudit('deal.amended')`. Add
  `product_id` to the line read + `LineItemView` so an edit preserves the catalogue link. *Verify:* tsc/eslint.
- **Phase 2 - form + entry + verify:** `EditDealForm` (create form shape, prefilled, MANDATORY note). An **Edit**
  button on the card (members only). On success, DealPin re-reads -> new version + gate reset. *Verify LIVE:*
  edit the 3.5a card, note required, version bumps, both seats reset to pending, old version frozen in the log.

## 4. Boundaries (what 3.5b does NOT do)

- **No new confirm logic** - the version bump resets 3d's gate; 3.5c only verifies/adds a "this changed" cue.
- **No `amended` status** (uses `draft` so 3d flips it; `amended` semantics are a later refinement).
- **No discount / CC / Sella** (parked, as in 3.5a). **No card UI rework** (3.5d).

## 5. Process

Foundation (RPC) first, verified by SQL; then the action; then the form + entry, verified LIVE in Preview
(restart the server after editing actions - the Turbopack stale-server-action gotcha). Wrap to docs at session end.
