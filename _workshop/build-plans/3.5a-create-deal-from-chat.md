## 1. Decisions locked with Ayush (carried in from the 2026-06-11 chat)

- **D1 - Anyone can create.** Buyer OR supplier can create a deal from a chat. The form is identical for both
  sides and NEVER asks "offer or order." Whoever clicks Create writes version 1 (a draft).
- **D2 - Recipient auto = the chat counterparty.** Created from inside a chat, so the "TO" is pre-filled and
  not chosen. A contact-selector SLOT is left in the form for the future shop/Sella entry point, but is NOT
  wired now.
- **D3 - Prices are OPTIONAL.** A card can be created and sent WITHOUT prices (two sides still just talking).
  If a price is on a line, it shows. The whole private-pricelist-DISCLOSURE machinery is OUT (bypassed); for
  the demo we use the price already on the seller's pricelist.
- **D4 - Private box per side (free cell).** The creator fills their own-side private number: SELLER = buying
  price from their supplier (-> margin = sell - buy); BUYER = price to the patient (-> margin = patient - buy).
  Each side only ever sees its OWN box. Stored in `deal_party_field` (owner-only RLS, already built).
- **D5 - Workspace spawns at DRAFT.** Confirmed by Ayush: the deal workspace is born the moment the draft is
  created (NOT at confirmation). No change from today's behaviour. (The stale "spawn at confirmation" note in
  KNOWN-AMENDMENTS gets corrected at wrap.)
- **D6 - The human Update/Create button is the only commit.** The write happens in a SERVER ACTION, triggered
  only by a human button press. Company derived from the SESSION, never from input (same guardrail as 3d). This
  is the AI fence: Sella may later FILL the form, but only a human's click runs the save.
- **D7 - A note is part of creation.** Creation writes one `deal_card_log` line (v1, "Deal created") plus the
  creator's note via `deal_change_input` (the same note primitive 3.5b makes mandatory for edits).
- **OUT (other parked items, confirm with Marcel later):** discount (% vs E, storage), price-list disclosure,
  precise buyer/seller labelling rule, HS-deal-number short-code rule. None block 3.5a.

## 3. Design points - RESOLVED with Ayush (2026-06-11)

- **Q-A - Card location = the chat's existing deal area (VERIFIED in code).** The deal area is `DealPin`,
  mounted in `ThreadView` (`ThreadView.tsx:65`) keyed by **relationshipId**. It calls
  `getCurrentDealCardId(relationshipId)` -> latest LIVE-status card for that relationship (or null). Null =>
  blank area. So a card belongs to a **RELATIONSHIP, not a thread** (that is why `deal_card.thread_id` is NULL
  on every existing card and the card still shows). **Create = write a `deal_card` with `relationship_id` = this
  chat's relationship; `thread_id` stays NULL** (consistent with all existing data). On the next load the deal
  area fills itself - no new placement, no thread wiring. The CREATE ENTRY POINT is the blank `DealPin` area in
  `ThreadView` (show a "Create a deal" affordance when `getCurrentDealCardId` is null), NOT the `DealChat`
  composer (that chat only exists once a deal is born). A `deal_started` system message is OPTIONAL polish, not
  required for the card to appear.
- **Q-B - HS deal number: leave NULL at draft.** The Layer 3 wording on number generation is treated as
  OUTDATED (Ayush) and parked. For 3.5a `hs_deal_number` stays NULL on the draft; we revisit number generation
  later. Non-blocking.
- **Q-C - No-price display = "Price TBD".** Sum the line totals that have a price; if no line has a price, leave
  `value_net` NULL and the card shows **"Price TBD"**. Leave a hook for a future **"request a price list"**
  affordance (ties to the parked price-list-disclosure flow) - not built in 3.5a.

## 6. Reusability / Sella-readiness note

`CreateDealForm` takes its initial values as a prop (`initial?: CreateDealInput`) and reports the final values
on the human's Create press. It has NO knowledge of where the initial values came from. Today: empty (human
types). Later: Sella feeds `initial`. Same form, different source - "dumb + fed," exactly like `ConfirmBar`.
