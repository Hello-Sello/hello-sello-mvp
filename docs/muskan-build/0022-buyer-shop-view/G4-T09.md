# ▶ RULE ON THESE

### 1. `pending_inbox_item` crosses ADR-0005's fence *(critic E1 — blocking, escalated)*
The ADR's Reused list says `pending_inbox_item` is *"reused via `metadata`; no new table, no new
type, **no migration**."* T09 gives it a column allowlist and re-creates `inbox_insert`.
**Why it happened:** without it the ticket's own remedy is defeated — the RPC reads consent from a
row the attacker can write. Holes 2 and 3 above are that fence being load-bearing.
**Verified safe independently by `critic`:** all 7 client UPDATE sites write only
`status`/`assigned_*`; both client INSERTs already pass `sender_person_id: uid`; `deliver_deal` is
DEFINER/postgres so policies never apply to it.
**Options:** (a) accept, amend the ADR fence · (b) split the `pending_inbox_item` half into its own
ticket — **but then T09 ships a gate whose consent evidence is still forgeable**, which is the exact
thing your T06 ruling forbade.

### 2. The verification **triple** vs a one-column criterion *(critic E2 — blocking, escalated)*
Criterion 4 names `verification_status`. The migration also removes `verified_at` and `verified_by`.
One fact — *who verified this company and when*. Leaving two writable lets a member forge the
verification audit trail while the status is locked. L-017 says widening a written criterion is a
deviation for the gate, so here it is. **Options:** accept as shipped · or narrow to the one column.

### 3. Re-accepting an already-accepted item now throws *(critic N5 — undeclared behaviour change)*
Pre-T09 the client adopted the live pair row regardless of item status. Now the RPC RAISEs. Reachable
from a second tab or a stale Discover list — and **neither UI entry point has a catch**
(`InboxView.tsx:137`, `RequestsSection.tsx:95-103`), so it degrades to a silent no-op with an
unhandled rejection. **That is DEV-83's exact shape.** Not caused by T09's logic, but T09 makes it
reachable. **Options:** accept + file · fix the catch here (small, but outside the declared files).

### 4. `pricelist_request` mints a **full** connection *(security — not a regression, but newly load-bearing)*
Matches pre-fix client behaviour. But post-T06 a relationship IS the catalogue-confidentiality gate,
so **"accept a price request" and "grant catalogue access" are now the same action.** Confirm that
is intended, or the RPC's type allowlist should drop `pricelist_request`.

### 5. `anon` holds TRUNCATE on ~90 tables *(security — out of scope, needs its own ticket)*
Deny-by-default was installed for **functions** (session 77) and **never for tables**. Proven with
real rows: `seeded audit rows: 3` → `set role anon; truncate public.audit_log cascade` → **`0 rows`**.
The append-only hash-chained audit log, gone. **Not reachable via PostgREST** (it emits neither
TRUNCATE nor DDL), so this is not a live exploit — it is one FK change away from mattering, and it
is the same class session 77 closed for functions. **Recommend: own ticket, not T09.**
