## ▶ Ruling 1 — the ADR fence (`critic` B1)

ADR-0005 `Reused` says `ShopView` takes *"no behavioural modification"*, and §6:576 repeats it.
The amendment you signed at G3 licenses **exactly one line** — and T02 spent it.

T04 adds three more to `ShopView`: an action import, a 10-line `handleRequestPricing`, and a
call-site prop. **Why it is unavoidable:** the ticket's Files list says `BuyerShopView.tsx` carries
the wiring, but `BuyerShopView` does not render `ProductCard` — `ShopView` does. Reaching the card
from there needs a new *prop* on `ShopView`, which the same ADR forbids more strongly. The chosen
shape copies `handleAddToBasket`, which already sits in that file for the identical reason.

`ShopView` still gains **no prop**. Options: amend the fence to "no new props; internal handlers
allowed", or reject and re-scope.

## ▶ Ruling 2 — DEV-83 is now on the demo path (`critic` B2)

**I got this wrong in the plan and the correction matters.** D8 said the crash needs a *second*
accept. For an **already-connected** buyer it fires on the **first** — and Bob, criterion 2's own
identity, is seeded connected.

Proven empirically, rolled-back transaction: `SQLSTATE 23505` on `uq_relationship_pair_active`.
The seeded relationship carries `inbox_item_id = NULL`, so `acceptInbox`'s probe (`store.ts:538`)
can never match it and falls through to the INSERT. The throw is **uncaught** —
`InboxView.tsx:137` is `void refreshWith(acceptItem(id))` — so the seller clicks Accept, **nothing
happens, no error**, the item stays `pending` forever, and the buyer cannot re-ask (the guard keys
on `pending`).

T04 does not create this — it is DEV-83, and a pending connect + pending pricing ask could already
collide. But between T02 and T04 no connected buyer could send a pricing ask at all, so T04 is what
makes it ordinary.

Not fixed here: `acceptInbox` serves **every** accept flow (connect, message, pricing, deal card).
Remedy is ~6 lines — adopt the existing pair relationship instead of inserting — but its test cost
is uncosted. Options: fix it now as part of shipping this slug, or ship T04 and block `/ship` on
DEV-83.

## ▶ Ruling 3 — the server accepts asks the UI would never offer (`critic` N1, `security` 4)

The card shows Request-pricing only when `!pricePublic`. The server accepts **any** visible product.
No confidentiality consequence — the note is server-authored from a name the buyer can already read
— and PRD §6.5 does not list this action among the server-enforced rules. But it makes the client
gate decoration, and ADR §7 pushed the *identical* `price_public` predicate server-side for basket
admission rather than trusting the card.

One line at `actions.ts:141` closes it: `if (product.price_public) return { error: … }`.
I corrected the overclaiming docstring either way. Options: add the line, or record it as
deliberate.
