Hello Sello — Phase 1 Database

A plain-English map of every table: what it holds, why it exists, and how it links to the others.

Status: All Phase 1 tables are ready to lock LOCK-READY . The Connect inbox (pending_inbox_item) was locked 2026-06-06 — 4 request types via the inbox_request_type lookup, a single assigned_to owner, and status pending / accepted / rejected. The small LOOKUP tables are just fixed lists of allowed values (so we can add options without changing the database).
PK primary key (the row's id) FK→ points at another table JSON flexible bag of fields ENC encrypted at rest UNIQUE no duplicates 🔒 = single source of truth
Shared by every table (shown dimmed, not repeated in words): id (a random UUID) · created_at / updated_at (when made / last changed) · deleted_at (“soft delete” — we hide rows, never truly erase, for the audit trail). Company-owned tables also carry company_id so each company only sees its own data. (The audit log is the one exception — it can never be edited or deleted.)

Roles & permissions

LOCK-READY person_group The join table: which people belong to which groups. Also where the platform “superadmin” role lives 🔒.
id PKuuid—
person_id FK→personuuidThe member.
group_id FK→groupuuid · nullThe group…
rolevarchar · null…or a platform role like superadmin (then group is empty).
created_at / deleted_attimestamptzRule: must have a group OR a role.
Why here? Keeping “superadmin” as a row (not a checkbox on person) means one source of truth and no self-promotion.

action FK→permission_actionvarcharThe action code (e.g. view_deals) — not the label.

created_by / updated_by FK→personuuid · nullWho set / last toggled the grant.
created_at / updated_attimestamptzUNIQUE per group+action.

Audit trail
LOCK-READY audit_log A permanent, tamper-evident record of every important action. Can never be edited or deleted. One table covers every kind of event.
id PKuuid—
sequence_numberbigserialEver-increasing counter — a gap signals tampering.
company_id FK→companyuuidWhich company this concerns.
actor_person_id FK→personuuid · nullWho did it (empty if it was the system/Sella).
actor_type lookupvarcharuser / hs_team / sella / system / webhook.
on_behalf_of_person_id FK→personuuid · nullThe human behind an automated action.
action lookupvarchare.g. company.verify_approved.
content_type lookup + content_idvarchar / uuidWhich thing it happened to (any table — that's “polymorphic”).
before_diff / after_diff JSONjsonbWhat changed.
reasontext · nullRequired for rejections — this is where the reject reason lives.
reverses_audit_id FK→audit_loguuid · nullIf this entry undoes an earlier one.
prev_entry_hash / entry_hashbyteaA hash chain — each row locks the one before it.
metadata / created_atjsonb / timestamptzNo deleted_at — it's immutable.
Powers: the rejection reason, licence view logs, HS-staff grants, and the “who did what” history everywhere.
LOOKUP ×3 audit_actor_type · audit_action_type · auditable_content_type The three fixed lists the audit log points at: who can act, what actions exist, and what kinds of things can be acted on.
audit_actor_typecode, descriptionuser / hs_team / sella / system / webhook.
audit_action_typecode, category…Stripe-style names like pricelist.published. New ones added as features ship.
auditable_content_typecode, target_tablecompany / person / deal_card… New phases just add rows here.
The big picture: almost everything points back at two tables — person (who) and company (which business). Roles hang off people, files & licences hang off companies, and audit_log quietly records what everyone does. Source of truth: docs/architecture/SCHEMA-DRAFT.md.
