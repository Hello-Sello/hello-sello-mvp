Email Integration — Research & Decision

Hello Sello · researched 2026-07-13 · owner: Muskan · status: proposed (pending Marcel + Ayush review, Unipile sales call)

1.The problem we are solving

Cold start + the core pitch. A user who joins Hello Sello today lands on an empty platform: no contacts, no conversations, no network. But our founding pitch is "buyers & sellers manage mails, fax and chat messages in one place" — email is the product, not an add-on.

Concrete September case: Canadian Craft (Marcel) onboards with ~25 pharmacy partners who are not on the platform and may never join. All of that business runs on email today. Without email integration, Marcel gets an empty tool; with it, his real business flows in from day one — and every pharmacy that emails him becomes a contact and a future signup lead.

Target experience ("email-as-chat"): user connects their real inbox once → incoming emails appear in Hello Sello as chat conversations → replies typed in Hello Sello go out as normal emails from the user's own address, in the same thread. The counterparty never knows Hello Sello exists. Sella reads the stream and turns conversations into deals.

2.How it can be solved (end-to-end shape)

[Pharmacy mailbox] ←→ [Outlook / Gmail / IMAP servers] ←→ [Email provider layer] ←→ [Hello Sello + Supabase] Connect (once): user clicks "Connect inbox" → OAuth login → provider layer stores tokens, returns account_id → we store only the account_id next to the person row Inbound (always): new email → webhook POST to our server (clean JSON: from, subject, body, thread id, attachments) → map sender→contact/company, thread→conversation → store as chat message → Sella reads it like any chat Outbound: reply typed in chat → send API call → goes out through the USER'S own mailbox → normal threaded email; also lands in their "Sent" folder Backfill (opt.): one-time history import at connect time (we choose default window, user picks: 3 mo / 12 mo / none — doubles as GDPR consent)

What we build: connect button + callback, one webhook handler, thread↔chat + sender↔contact mapping, send call, filtering (newsletters/no-reply ≠ chats), privacy defaults (imported mail follows the existing "personal chats never company-visible" lock). What the provider layer owns: OAuth tokens + refresh, provider differences, webhook subscription renewals, (depending on choice) Google's security review.

Scale~500≈ €1,500–2,500→ the point where migrating to EmailEngine / direct build wins
  • Billing is per connected inbox, not per app user or per message — predictable; users who never connect cost nothing.
  • Treat it as cost-of-goods: ~€5/user/mo for the entire communication backbone is a healthy slice of a B2B subscription. Watch out if a free tier lets people connect inboxes — every free connection has real marginal cost.
  • Exit ramp is planned, not hoped for: rent now → own the plumbing (EmailEngine ≈ "build direct with a head start") once volume justifies the CASA audit + ops. By then there's revenue to fund it.
Architecture rule that keeps the exit cheap: all Unipile specifics live inside ONE adapter module (email-channel: connectInbox(), onMessageReceived(), sendReply()). The rest of the codebase never mentions Unipile. Migrating later = rewriting one module, not the product.

7.Recommendation

✅ What we choose and why

  1. Email-as-chat via Unipile, email channel only. Fastest legitimate path to the core product for a 2-dev team before September: ~1–2 wks pipe + 3–6 wks product work (mapping, filtering, privacy, backfill UX, Sella wiring). EU vendor fits our market.
  2. Microsoft first-class from day one (Marcel's market is Outlook-heavy; publisher verification is cheap paperwork). Gmail works at pilot scale regardless (<100-account exemption).
  3. One adapter module so the scale-time migration (EmailEngine / direct) stays a module swap.
  4. WhatsApp deferred to official-API route post-launch. Fax stays post-MVP.

Before committing — the sales call checklist (Unipile)

  1. The make-or-break question, in writing: "Using your default hosted auth, do we ever need our own Google restricted-scope verification or CASA audit — yes/no, contractually?"
  2. Does the pre-verified credential cover full-inbox reading (restricted scope), not just send?
  3. DPA + exactly where mail data is processed/stored (EU?).
  4. If a user connects email and (later) another channel — one billed account or two?
  5. Rate limits / fair-use caps on bulk historical backfill.
  6. Volume-discount curve above 50 accounts.

And one question for Marcel

"Which email providers do Canadian Craft and the pharmacies actually use?" (Outlook/M365? Gmail? IONOS/T-Online/GMX?) — confirms the Microsoft-first bet and tells us how much IMAP matters at launch.
